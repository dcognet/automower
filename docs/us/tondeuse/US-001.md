## User story

En tant qu'opérateur, je veux lancer la CLI sur un fichier conforme qui décrit une pelouse et une tondeuse, afin d'obtenir la position et l'orientation finales de cette tondeuse.

## Incrément de valeur

Le cas nominal fonctionne de bout en bout pour une tondeuse : `java -jar mower.jar <fichier>` exécute ses instructions et affiche sa position finale. C'est le walking skeleton de la feature : il met en place le jar exécutable, les 3 couches et le rendu sur stdout.

## Critères d'acceptance

- [ ] CA-1 : étant donné le fichier `5 5` / `1 2 N` / `LFLFLFLFF` (la première tondeuse de l'exemple de référence), quand je lance la CLI, alors stdout contient exactement `1 3 N\n` et le code de sortie est `0`. *(réf. spec : RM-12, O-1)*
- [ ] CA-2 : `L` fait pivoter de 90° à gauche sans déplacer la tondeuse (`N → W → S → E → N`), `R` de 90° à droite (`N → E → S → W → N`). *(réf. spec : RM-05, RM-06)*
- [ ] CA-3 : `F` avance d'une case dans la direction de la tondeuse sans changer son orientation (`N` → `(X, Y+1)`, `E` → `(X+1, Y)`, `S` → `(X, Y-1)`, `W` → `(X-1, Y)`). *(réf. spec : RM-07)*
- [ ] CA-4 : les instructions s'exécutent une par une, dans l'ordre de la séquence. *(réf. spec : RM-09)*
- [ ] CA-5 : les bornes sont inclusives (`0 ≤ x ≤ Xmax`, `0 ≤ y ≤ Ymax`). Un `F` qui ferait sortir la tondeuse est ignoré sans erreur : la tondeuse garde sa position et son orientation, puis passe à l'instruction suivante. Exemple : pelouse `5 5`, tondeuse `5 3 E` avec la séquence `FL` → `5 3 N`. *(réf. spec : RM-02, RM-08 volet bord, O-2)*
- [ ] CA-6 : une pelouse rectangulaire est acceptée. Exemple : pelouse `5 3`, tondeuse `0 0 E` avec la séquence `FFFFFFL` → `5 0 N`. *(réf. spec : RM-01, RM-14)*
- [ ] CA-7 : la position finale est écrite au format `X Y O`, terminée par `\n`, quelle que soit la plateforme. *(réf. spec : RM-03, RM-04, RM-11)*

## Contraintes techniques (héritées du .tech.md)

- CLI Java 25 + Maven, jar exécutable sans framework applicatif. Point d'entrée `java -jar mower.jar <fichier>`, code de sortie `0` en cas de succès.
- Architecture hexagonale à 3 couches `domain` / `application` / `infrastructure`. Le domaine est pur, ce que vérifie `DomainPurityTest` (ArchUnit), à mettre en place dès cette US.
- Pipeline en deux phases : le modèle complet est construit avant la simulation, qui ne lève aucune erreur. Cas d'usage unique : `MowLawnUseCase`.
- Value objects en `record` immuables (`Lawn`, `Position`, `Mower`), enums `Orientation` et `Instruction`. La séquence reste une `String` parcourue caractère par caractère.
- Lecture du fichier en octets, décodage UTF-8 et découpage maison sur `\n` (avec retrait du `\r` qui le précède). Pas de `BufferedReader.readLine` ni de `Files.readAllLines`.
- Sortie via un writer UTF-8 explicite avec `\n` littéral. Pas de `System.out.println`.
- Tests : unitaires `shouldX_whenY` sur le domaine, `*IntegrationTest` qui lance le vrai point d'entrée.

## Hors scope

- Fichier qui décrit plusieurs tondeuses, et exemple de référence complet (US-tondeuse-008).
- Blocage par une autre tondeuse (US-tondeuse-002).
- Toute détection et tout rendu d'erreur (US-tondeuse-003 à US-tondeuse-006). Ici, l'entrée est supposée conforme.
- Tenue de charge à 10 Mo (US-tondeuse-007).
- Hors scope de la spec : génération de parcours, suivi des cases tondues, exécution simultanée, pilotage temps réel, autres obstacles.
