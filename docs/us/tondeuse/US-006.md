## User story

En tant qu'opérateur ou script d'automatisation, je veux qu'un fichier inexploitable ou un appel incorrect de la CLI produise une erreur explicite et un code de sortie non nul, afin de détecter l'échec sans analyser le contenu du fichier.

## Incrément de valeur

Tous les cas où le contenu ne peut pas être lu sont couverts, avec le format `ERROR: <description>` sans numéro de ligne et un code de sortie exploitable par un script.

## Critères d'acceptance

- [ ] CA-1 : un chemin absent, un chemin qui désigne un dossier ou un fichier illisible (droits refusés) donnent `ERROR: <description>\n`, sans numéro de ligne, et le code de sortie `1`. *(réf. spec : RM-20, RM-23, RM-32)*
- [ ] CA-2 : un fichier vide (0 octet) est rejeté. C'est une erreur sur le fichier entier, `ERROR: …` sans numéro de ligne. *(réf. spec : RM-20)*
- [ ] CA-3 : un fichier de 10 000 000 octets est accepté. Un fichier de 10 000 001 octets est rejeté avant toute lecture de son contenu, avec `ERROR: file size 10000001 bytes exceeds limit of 10000000 bytes`, même s'il contient aussi des erreurs de format. *(réf. spec : RM-27)*
- [ ] CA-4 : un fichier qui n'est pas de l'UTF-8 valide est rejeté avec `ERROR: …`, sans numéro de ligne. Un caractère non ASCII mais valide en UTF-8 (`é`, `５`) n'est pas une erreur d'encodage : il reste une erreur de format avec son numéro de ligne. *(réf. spec : RM-30)*
- [ ] CA-5 : les contrôles s'enchaînent dans cet ordre, chacun bloquant le suivant : chemin absent, dossier ou illisible → taille → encodage → erreurs de ligne. Une erreur sur le fichier entier prime toujours sur une erreur de ligne. *(réf. spec : RM-27 ; .tech.md § Lecture du fichier)*
- [ ] CA-6 : un appel avec zéro ou plusieurs arguments produit `ERROR: usage: mower <file>\n` sur stdout, avec le code de sortie `2`. Il n'y a pas de lecture sur l'entrée standard. *(.tech.md § Contrat de la CLI, hors spec)*
- [ ] CA-7 : la lecture du contenu est plafonnée à 10 000 001 octets, même si `Files.size` annonçait une taille conforme (fichier qui grossit entre le contrôle et la lecture, ou fichier spécial comme un pipe nommé ou `/proc/...`, qui annonce 0). Si plus de 10 000 000 octets sont lus, le fichier est rejeté avec l'erreur RM-27 et la mémoire consommée reste bornée. La taille réelle étant alors inconnue, le message est `ERROR: file size exceeds limit of 10000000 bytes`. *(réf. spec : RM-27)*

## Contraintes techniques (héritées du .tech.md)

- Ces contrôles relèvent de la couche `infrastructure` (lecture du fichier et point d'entrée CLI) et lèvent une `BusinessValidationException` sans numéro de ligne.
- La taille est lue via `Files.size` avant toute lecture du contenu, ce qui rejette tôt un fichier trop gros sans le charger.
- Le contenu est ensuite lu avec un plafond : `InputStream.readNBytes(10_000_001)`, puis rejet si plus de 10 000 000 octets ont été lus. Pas de `Files.readAllBytes`, qui chargerait tout le fichier si sa taille a changé depuis le contrôle.
- Le décodage passe par un `CharsetDecoder` UTF-8 en mode `REPORT`.
- Les fixtures en octets (UTF-8 invalide, fichier de 10 000 001 octets) sont générées par les tests et non commitées.
