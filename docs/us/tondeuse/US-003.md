## User story

En tant qu'opérateur, je veux qu'un fichier qui contient une ligne mal formée soit rejeté en entier, avec un message qui donne le numéro de la ligne en cause, afin de corriger le fichier sans obtenir de résultat partiel trompeur.

## Incrément de valeur

Les erreurs de syntaxe ligne à ligne sont détectées et restituées au format `ERROR line <n>: <description>`, avec un code de sortie non nul. Cette US met en place le mécanisme d'erreur métier (catalogue de codes et exception) que les US d'erreur suivantes enrichissent.

## Critères d'acceptance

- [ ] CA-1 : si une ligne est non conforme, aucune position finale n'est écrite, même pour les tondeuses qui la précèdent. Stdout contient une seule ligne `ERROR line <n>: <description>\n` en anglais, et le code de sortie est `1`. *(réf. spec : RM-13, RM-23, RM-32, O-3)*
- [ ] CA-2 : une instruction autre que `L`, `R` ou `F` est rejetée. Exemple : `LFA`, `lf` et `L F` sont rejetés. *(réf. spec : RM-16)*
- [ ] CA-3 : une orientation autre que `N`, `E`, `S` ou `W` est rejetée, minuscules comprises. Exemple : `1 2 n` est rejeté, et `1 2 X` en ligne 4 produit `ERROR line 4: invalid orientation 'X'`. *(réf. spec : RM-17, RM-32)*
- [ ] CA-4 : une coordonnée qui ne s'écrit pas `0|[1-9][0-9]*` en chiffres ASCII est rejetée, que ce soit dans la pelouse ou dans une position. Sont rejetés : `05`, `00`, `+3`, `-0`, `-1`, `５`, `٥`, `1.5`, `1e3`, `abc`, `5 A`. *(réf. spec : RM-19, RM-28)*
- [ ] CA-5 : les valeurs sont séparées par exactement une espace U+0020. Sont rejetés : tabulation, espace insécable, double espace, espace en début ou en fin de ligne. *(réf. spec : RM-29, RM-21 volet espaces)*
- [ ] CA-6 : la ligne de la pelouse a exactement 2 valeurs, une ligne de position exactement 3. Sont rejetés : `5`, `5 5 5`, `1 2`, `1 2 N X`, `1 2N`. *(réf. spec : RM-31)*
- [ ] CA-7 : une séquence d'instructions vide est rejetée sur sa ligne. *(réf. spec : RM-20)*
- [ ] CA-8 : une position sans ligne d'instructions est rejetée, et le numéro signalé est celui de la ligne attendue. Exemple : un fichier de 2 lignes `5 5` / `1 2 N` produit une erreur en ligne 3. *(réf. spec : RM-22)*
- [ ] CA-9 : un fichier qui définit la pelouse mais aucune tondeuse est rejeté. L'erreur est signalée en ligne 2, la ligne attendue. *(réf. spec : RM-20)*
- [ ] CA-10 : si le fichier contient plusieurs erreurs, seule la première dans l'ordre des lignes est signalée. *(réf. spec : RM-23)*

## Contraintes techniques (héritées du .tech.md)

- Catalogue `BusinessErrorCode` (un code stable par cause) et `BusinessValidationException`, qui porte le code, une description en anglais et un numéro de ligne optionnel. Jamais d'`IllegalArgumentException` pour une règle métier.
- L'analyse fait un seul passage dans l'ordre des lignes et s'arrête à la première erreur. Pas d'accumulation des erreurs.
- Chaque type de ligne est reconnu par une regex ancrée en ASCII explicite. La longueur d'une coordonnée est bornée avant conversion. Pas d'`Integer.parseInt` ni de `Scanner` sur une valeur non validée.
- `Orientation.fromCode` et `Instruction.fromCode` sont les seuls points de validation de ces valeurs fermées.
- Seul le point d'entrée traduit l'exception en texte RM-32 et en code de sortie `1`.

## Hors scope

- Fins de ligne, lignes vides et BOM (RM-21 volet lignes, RM-30 volet BOM) : traités dans US-tondeuse-004.
- Valeurs syntaxiquement correctes mais invalides (hors pelouse, pelouse `0 0`, bornes maximales, départs en doublon) : traitées dans US-tondeuse-005.
- Erreurs qui portent sur le fichier entier (absent, vide, taille, encodage) et usage de la CLI : traités dans US-tondeuse-006.
- Tolérance de format (normalisation, correction automatique) et traitement partiel : hors scope de la spec.
