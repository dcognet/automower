## User story

En tant qu'opérateur, je veux que les fichiers produits sous Unix comme sous Windows soient acceptés, et que les lignes vides, les fins de ligne exotiques et le BOM soient rejetés avec le numéro de ligne en cause, afin que le découpage des lignes soit strict et prévisible.

## Incrément de valeur

Un fichier écrit sous Windows (`\r\n`) donne le même résultat qu'un fichier Unix, et toute anomalie de structure des lignes est signalée précisément.

## Critères d'acceptance

- [x] CA-1 : les fins de ligne `\n` et `\r\n` sont acceptées, y compris mélangées dans un même fichier. L'exemple de référence en `\r\n` donne exactement `1 3 N\n5 1 E\n`. *(réf. spec : RM-21, RM-11)*
- [x] CA-2 : un unique saut de ligne final (`\n` ou `\r\n`) est accepté. Un fichier sans saut de ligne final est accepté lui aussi. *(réf. spec : RM-21)*
- [x] CA-3 : une ligne vide, au milieu du fichier ou issue d'un second saut de ligne final, est rejetée avec son numéro de ligne. *(réf. spec : RM-21)*
- [x] CA-4 : un `\r` isolé, qui n'est pas suivi de `\n`, est rejeté comme caractère invalide sur la ligne qui le contient. *(réf. spec : RM-21)*
- [x] CA-5 : un BOM UTF-8 en début de fichier est rejeté comme erreur de format sur la ligne 1. *(réf. spec : RM-30)*
- [x] CA-6 : un message d'erreur qui cite un caractère de contrôle (tabulation, `\r`, U+FEFF…) l'affiche sous une forme échappée, pour que le message reste sur une seule ligne lisible. *(réf. spec : RM-32 ; .tech.md § Sortie standard)*

## Contraintes techniques (héritées du .tech.md)

- Le découpage est fait maison, sur `\n`, en retirant un `\r` immédiatement avant. Un `\r` isolé reste dans la ligne et y est rejeté par l'analyse du fichier. Pas de `BufferedReader.readLine` ni de `Files.readAllLines`.
- Le BOM est décodé en U+FEFF et laissé à l'analyse du fichier, qui le rejette en ligne 1.
- Les fixtures en octets (BOM, `\r` isolé) sont générées par les tests et non commitées.

## Hors scope

- Fichier non UTF-8 (RM-30, erreur sur le fichier entier) : traité dans US-tondeuse-006.
- Erreurs de syntaxe des valeurs (US-tondeuse-003).
- Normalisation ou tolérance de format : hors scope de la spec.
